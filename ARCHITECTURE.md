# DiceFlow — Architecture Specification
## 1. Назначение
DiceFlow — ассистент для варгеймов, предназначенный для быстрых, удобных и приятных бросков кубиков.
Приложение уже имеет проверенную предыдущую версию. Новая версия развивает существующий продукт, сохраняя его основной workflow и улучшая UX, Game Feel, производительность и расширяемость.
Главные требования:
- мгновенный запуск;
- работа через браузер;
- установка на устройство как PWA;
- работа офлайн;
- минимальное энергопотребление;
- плавная 3D-графика и анимации;
- простая разработка и сопровождение с помощью AI;
- возможность расширения без переписывания ядра.
---
## 2. Архитектурные принципы
### Разделение логики и представления
Игровая логика не должна зависеть от React, Three.js, DOM, WebGL или конкретного способа отображения.
```text
DiceFlow Core
      │
      ├── Game State
      ├── Dice
      ├── Groups
      ├── Selection
      ├── Actions
      ├── History
      └── Undo / Redo

UI и rendering являются отдельными слоями.

                 DiceFlow Core
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
         UI         Renderer      Storage
       React       Three.js      IndexedDB

Данные важнее визуального состояния

Источник истины — состояние игры.

Визуальные объекты не являются источником игровых данных.

User Action
    ↓
Action
    ↓
Game State
    ↓
UI / Renderer

AI-friendly architecture

Код должен быть:

* модульным;
* типизированным;
* предсказуемым;
* с небольшими файлами и функциями;
* без скрытого состояния;
* с минимальным количеством магии;
* с чёткими интерфейсами между слоями.

Каждый модуль должен иметь одну понятную ответственность.

5. Core

Core — полностью независимый от платформы игровой движок DiceFlow.

Он не должен импортировать:

* React;
* Three.js;
* DOM API;
* WebGL;
* browser-specific APIs.

Core должен быть обычным TypeScript.

⸻

5.1 Dice

MVP использует только D6.

Однако модель кубика не должна быть жёстко привязана к шести значениям.

Концептуально:

Dice
├── id
├── type
├── value
├── selected
└── origin / operation metadata

В MVP:

DiceType = D6
Values = 1..6

Архитектура должна позволять в будущем иметь:

* D4;
* D6;
* D8;
* D10;
* D12;
* D20;
* специальные варгеймовые кубики;
* произвольные значения;
* дополнительные свойства граней.

Эта функциональность сейчас не реализуется.

6. Game State

Game State является единственным источником истины.

Он должен содержать только данные, необходимые для восстановления текущего состояния игры.

Концептуально:

GameState
├── dice
├── groups
├── selection
├── currentOperation
└── history

Render state не должен смешиваться с Game State.

Например:

"кубик сейчас вращается"

является состоянием Renderer, а не игровым состоянием.

8. Selection

Система выбора должна поддерживать:

* отдельный кубик;
* несколько кубиков;
* диапазон кубиков;
* всю группу;
* несколько групп;
* диапазон групп.

Selection является частью Game State.

Visual highlighting является ответственностью Renderer/UI.

Тап по уже выбранному кубику снимает выделение. Свайп с кубика на кубик выбирает диапазон между ними.

9. Actions

Все изменения состояния выполняются через действия.

Основные действия MVP:

Roll
ReRoll
Add
Delete
Move
Clear
Select
Undo
Redo

Каждое изменение должно быть представлено как понятная операция.

Это позволит:

* формировать историю;
* тестировать операции отдельно;
* воспроизводить состояния;
* упрощать работу AI с кодом.

10. Roll

Roll начинает новую итерацию броска.

Roll бросает выбранные кубики и удаляет все невыбранные — они больше не участвуют.

При отсутствии выбора кнопка Roll неактивна.

После получения значения кубик попадает в соответствующую группу.

Физическая симуляция кубиков не требуется.

Кубик визуально может вращаться, но результат определяется игровым ядром.

Roll
 ↓
Random values
 ↓
Game State update
 ↓
Renderer animation
 ↓
Final visual state

⸻

11. ReRoll

ReRoll перебрасывает выбранные кубики.

Если не выбран ни один кубик, ReRoll перебрасывает все кубики на столе.

selected dice
      ↓
new random values
      ↓
new groups

Предыдущие результаты сохраняются в истории операции.

⸻

12. Add

Количество добавляемых кубиков определяется выбором.

Selected = 5
→ Add 5

Если ничего не выбрано:

Add 1

Добавленные кубики получают случайное значение D6 и сразу попадают в соответствующую группу.

Удалённые значения запоминаются (стек LIFO): кубик, добавленный без явного значения, берёт значение последнего удалённого кубика, поэтому последовательность удалить→добавить не меняет значения. Память очищается действиями Roll, ReRoll и Clear.

Во время свайпа на пустом столе запоминаются выданные значения: если кубик удалён и затем снова добавлен в рамках того же жеста, он возвращается с прежним значением.

Последовательные нажатия Add и Delete в рамках одного раунда сворачиваются в одну net-запись. Например, «Add 5 → Delete 2 → Add 1» — одна запись «Add 4».

⸻

13. Delete

Если выбраны кубики:

Delete X

удаляются выбранные кубики.

Если выбор отсутствует, кнопка может использоваться для удаления последнего добавленного пользователем кубика.

Значения удалённых кубиков запоминаются, чтобы последующий Add вернул то же значение (см. Add).

⸻

14. Move

Move заменяет Boost.

Move позволяет переместить выбранные кубики в любую группу.

Selected dice
      ↓
Move
      ↓
Target group

Перетаскивание начинается после удержания кубика в течение input.dragDelayMs (по умолчанию 1000 мс). При перетаскивании (drag) захваченный кубик увеличивается и следует за курсором; если перемещается несколько кубиков, они собираются в компактную группу у курсора и следуют за ним. Это визуальное состояние Renderer и не влияет на игровое состояние.

Это изменение является логическим действием и должно отображаться в истории.

⸻

15. Enhance

Enhance увеличивает значение выбранных кубиков на единицу.

Enhance — частный случай Move (перемещение на +1). В текущем MVP не реализуется.

Поведение при достижении максимального значения должно быть определено отдельно в игровых правилах и не должно быть зашито в Renderer.

⸻

16. Undo / Redo

Undo и Redo работают независимо от пользовательской истории.

Undo/Redo не отображаются в History.

Undo:

Current State
     ↓
Previous State

Redo:

Previous State
     ↓
Next State

После нового действия после Undo ветка Redo удаляется.

Глубина Undo/Redo не ограничивается архитектурой.

Undo/Redo осуществляют переход по истории действий: отменяемы все действия, кроме выбора.

Последовательные одинаковые действия объединяются в один отменяемый шаг (например, пять нажатий «Add 1» — одно действие; свайп на пустом столе — одно действие).

⸻

17. History

History записывает каждое действие игрока: Roll, ReRoll, Add, Delete, Move и Clear.

Undo/Redo переходят по этой же истории и не записываются как отдельные записи.

Add и Delete в рамках одного раунда сворачиваются в одну net-запись: «Add 5 → Delete 2 → Add 1» записывается как «Add 4».

Пример строки броска:

20d6 → Roll → 4d6:6 → ReRoll → 2d6:6 → Explode

4d6:6 означает:

4 кубика со значением 6

⸻

18. Info Panel

Верхняя строка интерфейса отображает три сегмента по порядку:

Всего → изменения → Выделено

- общее число кубиков на столе;
- изменения с последнего Roll или Clear;
- число выбранных кубиков.

Сегмент изменений показывает только действия, выполненные с момента последнего Roll или Clear (Move, Add, Delete, ReRoll). После Roll или Clear он пуст до следующей модификации.

Верхняя область интерфейса не обязана постоянно показывать History.

Она является информационной областью и в будущем может отображать различные режимы:

History
Statistics
Current results
Quotes
Messages

Пример History:

20d6 → Roll → 4d6:6 → ReRoll

Пример информации:

20 D6
6: 4
5: 3
4: 5
3: 2
2: 3
1: 3

Пример декоративного контента:

"Лучше умереть за Императора,
чем жить для себя."

История является опциональной частью UX.

19. Operation Colors

Операции после первого броска должны визуально различаться.

Например:

Roll
ReRoll
Move
Explode

могут получать разные оттенки.

Кубики, созданные или изменённые соответствующей операцией, получают тот же визуальный оттенок.

Цветовая система должна быть централизованной и не зашиваться непосредственно в игровые операции.

21. Input

Input Layer преобразует действия пользователя в команды приложения.

Он должен быть отделён от Core.

Поддерживаемые взаимодействия:

Tap
Long Press
Drag
Swipe
Group Tap
Group Swipe

Конкретные жесты могут изменяться без изменения Core.

Различение жестов на кубике:

- тап (отпустил до движения за dragThresholdPx и до истечения dragDelayMs) — выбор;
- свайп (движение за dragThresholdPx до истечения dragDelayMs) — выбор диапазона от начального до текущего кубика, обновляется в реальном времени по мере движения пальца; после начала свайпа перетаскивание больше не активируется;
- удержание (прошло dragDelayMs до движения за порог) — начало перетаскивания.

Задержка перед перетаскиванием настраивается через input.dragDelayMs (по умолчанию 1000 мс).

Тап по уже выбранному кубику снимает выделение.

Свайп по группам (group swipe) выбирает диапазон групп от начальной до текущей, так же обновляясь в реальном времени.

22. Empty Table

Если поле пустое, отображается:

Swipe Finger to Add or Reduse Dices

Свайп работает только когда стол полностью пуст — после запуска или после Clear.

Пока палец находится на экране, количество кубиков изменяется в соответствии с движением.

Кубики сразу появляются в соответствующих группах.

Выданные значения запоминаются: кубик, удалённый и затем снова добавленный в рамках того же жеста, возвращается с прежним значением.

После отпускания пальца количество кубиков фиксируется, и весь жест считается одним действием.

24. Renderer

Three.js отвечает только за визуальное представление.

Renderer получает состояние и отображает его.

Game State
    ↓
Renderer
    ↓
Three.js Scene

Renderer отвечает за:

* 3D-кубики;
* камеру;
* материалы;
* освещение;
* анимации;
* частицы;
* визуальное выделение;
* визуальный захват при перетаскивании;
* перемещение между группами;
* эффекты.

Renderer не принимает решения о результате броска.

⸻

25. Rendering Loop

DiceFlow не должен постоянно рендерить сцену.

Состояние:

IDLE

означает отсутствие постоянного render loop.

При необходимости:

IDLE
 ↓
ACTION
 ↓
requestAnimationFrame()
 ↓
Animation
 ↓
Finished
 ↓
IDLE

Rendering запускается только при:

* анимации;
* взаимодействии;
* перемещении;
* броске;
* эффектах;
* изменении визуального состояния.

Это необходимо для снижения энергопотребления.

WebGL-контекст не следует уничтожать при переходе в IDLE.

⸻

42. Главное архитектурное правило

DiceFlow должен состоять из трёх независимых концептуальных уровней:

┌───────────────────────────────┐
│             UI                │
│       React / Input           │
├───────────────────────────────┤
│          GAME CORE             │
│          TypeScript            │
├───────────────────────────────┤
│          RENDERER              │
│       Three.js / WebGL         │
└───────────────────────────────┘

Game Core определяет, что произошло.

Renderer определяет, как это выглядит.

UI определяет, как пользователь взаимодействует с приложением.

Ни один из этих уровней не должен брать на себя ответственность другого.
